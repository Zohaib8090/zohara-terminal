# CLAUDE.md

Instructions for Claude Code (or any agent) working in this repo.

## What this is

Zohara Terminal: a universal terminal application for Arch-based Linux
(spec in `docs/SPEC.md`). A 25-crate Rust workspace, layered
**core → services → plugins → app**, dependencies only ever flowing one
direction. Two real front ends exist: `ut-tui` (ratatui, terminal-hosted)
and `ut-gui` (eframe/egui, a real native OS window) — both are thin
rendering/input layers over the same `ut_tui::App` state machine, which
itself is built on `ut-session`/`ut-ui`/`ut-safety`.

Read `README.md` first — it has the full crate tree, the "why the split is
where it is" reasoning, and the up-to-date "what's not here yet" list.
Read `ROADMAP.md` for what's done vs. remaining, prioritized.
Read `GOTCHAS.md` before touching PTYs, threading, or anything
GUI/Xvfb-related — every entry there cost real debugging time once.

## Build / test / lint

```sh
cargo build --workspace
cargo test --workspace       # all offline/hermetic by default
cargo clippy --workspace --all-targets
```

Keep `clippy --workspace --all-targets` clean before committing — this
repo has stayed at zero warnings throughout; don't be the first commit
that isn't.

### What `cargo test --workspace` does and doesn't need

- **Needs nothing beyond a C toolchain + `libssl-dev`** (for `ssh2`/
  libssh2 in `ut-plugin-ssh`). No network, no display, no extra shells —
  everything in the default run is offline and hermetic.
- `ut-plugin-loader`'s end-to-end test shells out to a real `cargo build
  -p ut-plugin-loader-fixture` and `dlopen`s the resulting `.so` — still
  hermetic (no network, no external service), just slower than a pure
  unit test the first time it's not already built.
- `ut-pty`/`ut-session`/`ut-daemon` tests spawn real local processes
  (`/bin/sh`, `/bin/cat`) — this is expected and always safe.
- `ut-plugin-ssh`'s live-connection tests (`SshClient::connect`/`exec`,
  SFTP, both port-forward directions) are `#[ignore]`d — they need a real
  reachable `sshd`. See "Re-verifying infra-dependent things" below.
- `ut-plugin-workflow`'s Bash/Zsh/Fish export tests run the generated
  script through the real interpreter **when it's installed**, and skip
  cleanly (not fail) otherwise — see `export.rs`'s `run()`/
  `skip_if_missing!`. Don't "fix" a skip by hard-requiring the shell; that
  was a deliberate choice (see GOTCHAS.md).
- `ut-gui`/`ut-tui` don't need a display to build or `cargo test`; only
  running the actual binary does (see Xvfb notes below).

## Conventions this codebase actually follows

- **One crate, one job, named `ut-<thing>`.** Before adding code, find
  which existing crate it belongs to by what it *owns*, not what feature
  it's for — e.g. port forwarding went into `ut-plugin-ssh::forward`
  (extends the SSH connection it already owns), not a new crate.
- **Every module-level `//!` doc explains *why*, not just what.** Read the
  top of a file before touching it — the reasoning for non-obvious
  decisions (threading model, security boundary, test strategy) lives
  there, not in a separate design doc.
- **New functionality ships with tests that exercise it for real**,
  against a real shell, a real PTY, a real local server, or (for GUI work)
  a real rendered screenshot — not mocks standing in for something a real
  instance could have driven. If something truly can't be exercised for
  real in CI (PowerShell generation, no `pwsh` here), say so explicitly in
  the doc comment and keep the test structural rather than pretending it's
  behavioral.
- **Commands never reach a shell unchecked.** `ut-session::Pane::submit_input`
  is the only write path into a PTY that's expected to run `ut-safety`
  first. If you add a new way to send input to a shell, either route it
  through `submit_input`/`Pane::write_raw` (and document why `write_raw`'s
  bypass is appropriate there — see its doc comment) rather than inventing
  a third path.
- **Plugins only ever see a `PluginContext`.** Never give a plugin direct
  access to `ut-session`/`ut-pty`/the filesystem — widen `PluginContext`
  instead, in one place, so every plugin's capability is auditable from
  `ut-plugin-api` alone.
- **Attribution**: do not put model names, "Generated by Claude", or
  similar in commit messages, code comments, or anything pushed to the
  repo. If the user has told you (in chat) to commit under their own name/
  email, keep doing that for the rest of the session — it's a durable
  instruction, not a one-off.

## Re-verifying infra-dependent things

These aren't required for normal development, only if you're touching the
code they cover and want the same level of proof this repo was built
with.

### A local test `sshd` (for `ut-plugin-ssh`'s ignored tests)

```sh
apt-get install -y --no-install-recommends openssh-server openssh-client openssh-sftp-server
# (if apt 404s on *-security packages, retry pinned to the plain `noble/main`
#  version shown by `apt-cache policy <pkg>` — a known flake in this sandbox,
#  not a real package problem)

mkdir -p /tmp/sshd_test/etc /tmp/sshd_test/run /run/sshd
ssh-keygen -t ed25519 -f /tmp/sshd_test/etc/host_key -N "" -q
ssh-keygen -t ed25519 -f /tmp/sshd_test/client_key -N "" -q
cat > /tmp/sshd_test/etc/sshd_config <<EOF
Port 2222
ListenAddress 127.0.0.1
HostKey /tmp/sshd_test/etc/host_key
PidFile /tmp/sshd_test/run/sshd.pid
AuthorizedKeysFile /tmp/sshd_test/authorized_keys
PasswordAuthentication yes
PermitRootLogin yes
UsePAM no
AllowTcpForwarding yes
GatewayPorts yes
Subsystem sftp /usr/lib/openssh/sftp-server
StrictModes no
EOF
cp /tmp/sshd_test/client_key.pub /tmp/sshd_test/authorized_keys
chmod 600 /tmp/sshd_test/etc/host_key /tmp/sshd_test/client_key
/usr/sbin/sshd -f /tmp/sshd_test/etc/sshd_config -D -e > /tmp/sshd_test/sshd.log 2>&1 &

cargo test -p ut-plugin-ssh -- --ignored
# tear down: kill the sshd pid, rm -rf /tmp/sshd_test when done
```

### Xvfb (for actually running `ut-gui`, not just building it)

```sh
apt-get install -y xvfb libxkbcommon-x11-0   # Mesa/llvmpipe software rendering, no GPU needed
xvfb-run -a -s "-screen 0 1000x640x24" cargo run -p ut-gui -- \
    --screenshot /tmp/out.png --exit-after-frames 20 --auto-type 'echo hello'
# then Read /tmp/out.png to actually look at it — don't just check exit code
```

See `ut-gui/src/main.rs`'s doc comment for the full list of verification
flags (`--auto-split`, `--open-palette`, `--palette-confirm`, ...).

### `zsh`/`fish` (for `ut-plugin-workflow`'s export tests to actually run, not skip)

```sh
apt-get install -y --no-install-recommends zsh fish
# fish pulls in bsdextrautils, which may hit the same *-security 404 —
# pin it: apt-get install -y bsdextrautils=<the non-security version> fish
```
