# .roadmap.md

What's built vs. what's left, mapped to `docs/SPEC.md`'s sections. Updated
as of commit `5c1d246` on `claude/upbeat-sagan-bfhhua`. See `HANDOFF.md`
for how to continue this, `GOTCHAS.md` for traps to avoid, `README.md` for
the crate-by-crate architecture.

## Done (27 crates, 319+ tests, all verified against something real)

### Core (Section 3 "Terminal compatibility", Section 10 "Command safety")
- `ut-pty` — real PTY spawn/read/write/resize via `nix`/`libc`.
- `ut-ansi` — ANSI/VT byte stream → typed events (vte-based).
- `ut-grid` — events → cell grid, cursor, scrollback, modes.
- `ut-config` — profile schema with inheritance, TOML load/save/validate.
- `ut-safety` — destructive-command & safe-paste analysis (the lexer +
  rule engine every write path is gated behind).

### Services (Section 4 "Windows/tabs/panes", Section 13 "Multiplexing", Section 7 "History")
- `ut-session` — PTY-backed panes/tabs/workspaces; `Pane::submit_input` is
  the one safety-checked write path.
- `ut-daemon` — the real multiplexer: named sessions in background
  threads, detach/reattach over a Unix socket.
- `ut-history` — command history store + search.
- `ut-search` — scrollback/output search, literal or regex.
- `ut-profile` — atomic config load/save, active-profile resolution.
- `ut-notify` — notification dispatch, suppression rules, history.

### Plugins (Section 12 "SSH", Section 14 "Workflows", Section 15 "AI", Section 19 "Plugins")
- `ut-plugin-api` — the `Plugin` trait + permission-scoped `PluginContext`.
- `ut-plugin-signing` — ed25519 manifest signing/verification.
- `ut-plugin-loader` (+ `ut-plugin-loader-fixture` for tests) — loads a
  `.so` behind `ut-plugin-signing`'s verification, over a stable C ABI
  (never a raw Rust trait object across the dylib boundary). Wired all the
  way into `ut-tui::App::load_plugins_from_dir`/`notify_plugins_of_command`/
  `pump_all` — a loaded plugin really does see every command and output
  chunk as they happen, it just can't execute anything itself. Verified
  by building the fixture crate as a real cdylib, signing and loading it
  through `App`, and driving real keystrokes/shell output through it.
- `ssh` (`ut-plugin-ssh`) — `SshClient` (connect/auth/exec), known-hosts
  verification, SFTP browser, local, remote, **and dynamic (SOCKS5)**
  port forwarding (`ssh -D`). The SOCKS5 handshake parser has its own
  default-run tests; the full tunnel is verified against a real `sshd`
  with a hand-rolled SOCKS5 client, like the other two forward directions.
- `package-manager` — pacman/checkupdates output parsing.
- `workflow` (`ut-plugin-workflow`) — command-sequence engine + JSON/YAML
  round-trip + Bash/Zsh/Fish/PowerShell export (Bash/Zsh/Fish verified by
  actually running the generated scripts).
- `ai` (`ut-plugin-ai`) — offline explainer + Ollama-backed `NetworkAssistant`.

### App (Section 4 "Windows", Section 20 "Command palette")
- `ut-input` — keyboard event → PTY byte sequence.
- `ut-renderer` — Grid → ANSI text + damage/diff tracking.
- `ut-ui` — pane split-tree layout (pure data).
- `ut-palette` — fuzzy command palette (fzf-style scoring, recent/
  favorites/aliases).
- `ut-tui` — real interactive multiplexer UI (ratatui).
- `ut-gui` — real native OS window (eframe/egui), reusing `ut-tui::App`.
- `ut-cli` — `zohara check`/`zohara paste` safety CLI.
- `ut-app` — `run`, spawns a real command through the whole core stack.

## Remaining, roughly by leverage (pick from here, or ask the user)

1. **SSH: ProxyJump chaining.** Dynamic (SOCKS) forwarding is done (see
   above). `ut-plugin-ssh` already parses `ProxyJump` out of an SSH
   config file and flags when a host profile uses one; nothing yet
   actually connects through the jump host first — needs a
   `channel_direct_tcpip` hop from the jump host's session feeding the
   final host's `SshClient::connect`, conceptually similar to how
   `local_forward` tunnels an arbitrary TCP destination today.
2. **Second AI backend + structured command generation.** `OllamaProvider`
   works; no llama.cpp/remote-provider backend yet (the `AiProvider` trait
   is what a second backend implements), and `NetworkAssistant.ask()`
   returns raw model text rather than structured "here's a command,
   confirm to run it".
3. **GUI polish.** `ut-gui` is one plain window: no multi-window/tray/
   dropdown/PiP, no mouse-driven pane resize (keyboard-only via Ctrl+B),
   no theme/font settings (colors hardcoded), no on-screen keyboard
   toolbar. Also doesn't expose `App::load_plugins_from_dir` yet (no
   menu/flag to point it at a plugin directory) even though the wiring
   under it is done.
4. **Command palette breadth.** `ut-palette` only has hardcoded app
   actions right now — wiring in tabs/SSH hosts/saved workflows/files/
   settings/history as searchable items is "feed more `PaletteItem`s into
   the registry the app already owns", not new architecture. Natural-
   language action search needs an AI backend wired to the palette.
5. **Visual workflow editor.** The execution engine and JSON/YAML
   round-trip exist (`ut-plugin-workflow`); no GUI editor for building a
   workflow visually.
6. **Everything with zero code yet**, roughly in spec order:
   - Beginner mode (first-run tutorial, visual task cards, beginner
     toolbar, command explanations) — blocked on a real GUI existing,
     which it now does, so this is more tractable than it used to be.
   - Package-manager *transactions* (actually running pacman installs/
     removes/upgrades through the safety-gated path) — `package-manager`
     currently only parses output, doesn't execute anything.
   - System tools (hardware info, service manager, firewall manager,
     backup/snapshot manager, log viewer).
   - Recovery & diagnostics (recovery terminal, safe-mode, support bundles).
   - Accessibility (screen reader, RTL/Arabic/Urdu rendering, high-contrast
     themes) — depends on the GUI's rendering layer maturing.
   - Localization (no i18n framework in place at all).
   - Command blocks UI (grouping command+output, collapse/bookmark/export
     — `ut-history` has the data; no block-rendering UI).
   - Encrypted history/workspace storage, secret redaction, clipboard
     timeout — everything is plaintext today.

## Not on the list (deliberately out of scope, not forgotten)

- A second native GUI toolkit — `ut-gui` (egui) is the one native front
  end; there's no reason to build a second unless requirements change.
- Windows/macOS support — `ut-pty` is Unix-only by design (`nix`/`libc`
  directly); this is an Arch-Linux-targeted project per the spec.
